# Engineering rules

- Work on one agreed phase at a time. Give the owner testing instructions at its checkpoint and wait for their direction before the next phase.
- Use React/Vite, strict TypeScript, TanStack Query for server state, and shadcn/ui as the planned accessible primitive foundation.
- Verify current stable versions, peer compatibility, and licenses when installing. Commit one package-manager lockfile and use frozen installs in CI.
- Organize by feature; share components only where a real repeated pattern exists. Keep API contracts generated from the backend's versioned schema artifacts.
- Establish typography, spacing, color, focus, and motion tokens before screen composition. Reuse page headers, controls, forms, tables, and status treatments.
- Aim for a restrained, professional clinic operations interface. Do not fill the product with decorative gradients, invented metrics, generic cards, or misleading working states.
- Review BoardUI, Thinking Orbs, React Bits, and Lenis against actual interaction needs and licenses. Prefer one coherent primitive system over mixing competing component libraries.
- Support keyboard navigation, visible focus, responsive layouts, reduced motion, and explicit loading/empty/error states.
- Urdu data works in the English MVP: use direction-aware layout, `dir="auto"` on mixed text, and Noto Nastaliq Urdu with adequate line height.
- Do not place provider secrets in browser environment variables. Validate public configuration and avoid persisting patient content in browser storage by default.
- Verify critical staff and voice-session flows with meaningful interaction tests; visually inspect relevant viewport sizes and mixed-script content before claiming completion.
- Follow CONTRIBUTING.md. Do not call Phase 0 complete without real voice measurements and human voice review.
